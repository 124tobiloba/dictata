  <decision>Confirm that pointing storage at a new folder moves the record and leaves no second copy, using copy → read-back verify → pointer commit → delete old.</decision>
  <context>
D-14 is marked one-way: undoing requires moving the user's data back and repairing a pointer file, and a half-finished move must never lose the record. The next task implements a `storage.json` pointer in `userData` (never inside the store folder), a `pendingDelete` journal entry written before the copy, a byte/length read-back verification, an atomically written pointer, and deletion of the old files only after the new copy is verified. `renameSync` is rejected because a network share or second drive is an explicit COMP-02 target and rename is same-filesystem only.
  </context>
  <options>
    <option id="copy-verify-delete">
      <name>Copy → verify → pointer commit → delete (recommended)</name>
      <pros>Works across volumes and network shares; a crash at any step leaves a recoverable record; the journal lets the next launch finish the deletion safely.</pros>
      <cons>Momentarily uses double the disk space; needs a verification pass and a journal.</cons>
    </option>
    <option id="rename">
      <name>Rename the store file</name>
      <pros>Atomic on one volume and simpler.</pros>
      <cons>Fails with EXDEV across volumes; a partially completed move can leave the app reading an empty or missing store; no verification step.</cons>
    </option>
  </options>
  <resume-signal>Select: copy-verify-delete (or describe a different verified-move design)</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| transcribed text → exported file | Attacker-influenceable text becomes a spreadsheet cell or file content |
| settings renderer → main process IPC | A renderer requests an export path or a storage move |
| user-chosen directory → filesystem | An arbitrary path becomes the destination of a copy and a delete |
| audit ledger → exported audit file | Long-lived metadata crosses into a hand-off artifact |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-11 | Tampering | `exporter.csvField` / `toCsv` | high | mitigate | A leading `=`, `+`, `-`, `@`, tab or CR is prefixed with a single quote; every text field is quoted per RFC 4180 with doubled quotes; CRLF rows and a UTF-8 BOM are emitted; tests assert all four. |
| T-01-12 | Tampering | `vf:choose-storage-dir` / `moveTo` destination | high | mitigate | The path originates in a native dialog in the main process and is never taken from renderer markup; `realpathSync` + `path.relative` containment rejects `userData` overlaps and traversal; `COPYFILE_EXCL` refuses to overwrite an existing store; a writability probe runs before the copy. |
| T-01-13 | Data loss / Tampering | `storage.moveTo` crash windows | high | mitigate | Journal written before the copy; verification (parse + history count + byte length + ledger count) before the pointer commit; old files deleted only after the commit; `finishPendingDelete` only deletes when the new copy verifies, and a corrupt pointer falls back to the default instead of aborting launch. |
| T-01-14 | Information disclosure | History export payload | medium | mitigate | Export projections are built from `history`/ledger records only — never settings, `dashboardToken` or the API key; the ledger export reads only allow-listed metadata fields. |
| T-01-15 | Information disclosure | Old store copy after a move | high | mitigate | The old files are deleted after the pointer commit and the journal is cleared; a restart completes a leftover `pendingDelete`, so no silent second copy remains. |
| T-01-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package changes in this phase; `npm install` must not run. Any future dependency requires the package-legitimacy gate and a blocking human checkpoint. |
</threat_model>
