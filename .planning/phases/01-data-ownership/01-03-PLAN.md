<task type="checkpoint:decision" gate="blocking">
  <name>Confirm storage relocation moves rather than copies (D-14)</name>
  <decision>Confirm that pointing storage at a new folder moves the record and leaves no second copy, and that every candidate design proves the new copy reads back before any old file is deleted.</decision>
  <context>
D-14 is marked one-way: undoing requires moving the user's data back and repairing a pointer file, and a half-finished move must never lose the record. Its non-negotiable rule is write to the new location → verify it reads back → only then remove the old copy. Both options below satisfy that rule; they differ in how a partially written target is kept out of sight. `fs.renameSync` is rejected outright by RESEARCH Q4: a network share or a second drive is an explicit COMP-02 target and rename is same-filesystem only (`EXDEV`), and a rename that partially succeeds is not "verify then delete".

Both options use the same journal contract, because it is what makes the crash windows safe: `storage.json` holds `{ version, dir, pendingDelete, move }` where `move` is `{ from, to, bytes, historyCount, ledgerLines }`. The journal is written before the first copy, but it records the intended pair in `move` and leaves `dir` pointing at the source. The pointer's `dir` and its `pendingDelete: [from]` only change in the single commit write that happens after the target verifies. Recovery (`recoverMove`) is therefore able to tell "interrupted copy" (source is still authoritative) from "committed move" (target is authoritative), and it deletes a pendingDelete entry only when that entry is not the directory the pointer currently resolves to.
  </context>
  <options>
    <option id="copy-verify-delete">
      <name>Copy → verify → commit → delete (recommended)</name>
      <pros>Works across volumes and network shares; the read-back verification (parse the new store, compare history length and pre-copy byte length, compare ledger line count) runs before the single commit write; recovery discards only the partial target files it created and leaves the source untouched.</pros>
      <cons>Momentarily double disk usage and, if the process dies mid-copy, a partial `dictata.json` sits at the target path until the next launch's recovery deletes it and clears the journal.</cons>
    </option>
    <option id="staged-verify-delete">
      <name>Copy to a staged name → verify → rename into place → commit → delete</name>
      <pros>Same cross-volume copy and same read-back verification, but the copy lands as `dictata.json.moving` and is renamed into place inside the target only after it verifies, so the real filename never holds a partial file; recovery deletes only the `.moving` files.</pros>
      <cons>One more step and one more journal state to reason about; the final rename still only works because both paths are inside the target directory, and a crash between rename and commit still relies on the same re-verify logic.</cons>
    </option>
  </options>
  <resume-signal>Select: copy-verify-delete (or staged-verify-delete; any other answer must still verify read-back before deleting the old copy, and must still keep `dir` on the source until the commit)</resume-signal>
</task>

storage.js (new, fs/path only so `node:test` can use temp directories): export `createStorage({ userDataDir })` plus the pure helper `samePath(a, b)` (compare `path.resolve` output, case-insensitively on `win32`, never a string prefix). It owns `storage.json` in `userDataDir` with the shape `{ version: 1, dir, pendingDelete: [], move: null }`, where `move` is `null` or `{ from, to, bytes, historyCount, ledgerLines }` — the record of a copy in progress. `readPointer()` parses defensively, normalises a missing `pendingDelete` to `[]` and a missing `move` to `null`, and falls back to the default pointer on any error (never abort launch). `currentDir()` returns the resolved directory. `setFile` on the store and the ledger follows a successful move; nothing else about the store changes.

The crash-safety contract, which must not be reordered:

1. `moveTo` writes the journal BEFORE copying anything, but it records the intent in `move` and leaves `dir` pointing at the SOURCE. `pendingDelete` is populated only by the commit, never by the pre-copy journal. Writing `pendingDelete: [oldDir]` while `dir` still equals `oldDir` is the exact bug this contract forbids: recovery would verify the source against itself and then delete it.
2. Authority moves in exactly one atomic pointer write — the commit — after the target has verified. That write sets `dir: to` and `pendingDelete: [from]` together.
3. The source files are deleted only after the commit. Before the commit they are the last known-good copy; after it they are the second copy D-14 forbids.
4. Recovery never deletes the directory the pointer currently resolves to, and never deletes a `from` it has not proved is superseded.
5. A partial target is disposable and identifiable: the move refuses to start when the target already holds `dictata.json`, so any `dictata.json` at `move.to` that fails verification was written by this move and can be removed.

`verifyCopy(move)` returns true only when `move.to/dictata.json` exists, parses into an object whose `history` is an array, `fs.statSync(...).size === move.bytes`, `history.length === move.historyCount`, and the line count of `move.to/dictata-audit.ndjson` equals `move.ledgerLines` (0 when that file is absent). All three signals are carried in the journal precisely so verification still works after a crash, when the original in-memory expectations are gone.

`resolveStoreDir()`: read the pointer; when `move` is non-null run `recoverMove`; then run `finishPendingDelete`; write the pointer back when either step changed it; return `pointer.dir`.

`recoverMove(pointer)`: if `verifyCopy(pointer.move)` succeeds, write `{ version: 1, dir: move.to, pendingDelete: [move.from], move: null }` and let `finishPendingDelete` remove the source. If it fails, delete ONLY the files this move could have created at `move.to` — `dictata.json`, `dictata-audit.ndjson`, `dictata.json.moving`, `dictata-audit.ndjson.moving` — and only when `samePath(move.to, pointer.dir)` is false, then write `{ ...pointer, move: null }` and leave `dir` on the source. Never delete the source here: an interrupted copy has no verified second copy, so the source is the record.

`finishPendingDelete(pointer)`: for each directory `d` in `pointer.pendingDelete`, skip when `samePath(d, pointer.dir)` (the pointer still resolves there, so this is the live store, not an old copy); skip when `pointer.dir/dictata.json` is missing or does not parse (nothing has proved the new copy is usable); otherwise delete the FILES `d/dictata.json` and `d/dictata-audit.ndjson` (never `rmSync` a directory), treating an already-absent file as a no-op (`fs.rmSync(file, { force: true })`) so a crash between the delete and the pointer rewrite cannot make the next launch throw, then rewrite the pointer with `pendingDelete: []`. Every pointer write in this module — the commit, the recovery rewrite, and this cleanup rewrite — goes through the same tmp+rename helper used by `moveTo`; a torn recovery write would otherwise hit `readPointer`'s default fallback while the record lives elsewhere.

`moveTo(targetDir)` performs, in order: reject a non-absolute string; `fs.realpathSync` the target; reject when `path.extname` of the resolved target is `.json`, `.ndjson` or `.tmp` (a file was passed, not a folder); reject when an existing resolved target is not a directory; reject containment with `userDataDir` or with the current store dir using `path.relative(...)` (`''` or a value that neither starts with `'..'` nor is absolute means "inside"); reject when `samePath(target, currentDir())`; reject when the target already holds a `dictata.json`; probe writability by writing and removing a `.dictata-probe` file; read `bytes = fs.statSync(oldStoreFile).size`, `historyCount = JSON.parse(oldStoreFile).history.length` and `ledgerLines` from the old ledger; write the journal with `move: { from: oldDir, to: resolvedTarget, bytes, historyCount, ledgerLines }` and the unchanged `dir`/`pendingDelete` atomically (tmp + rename); copy `dictata.json` and `dictata-audit.ndjson` when present with `fs.constants.COPYFILE_EXCL`; run `verifyCopy(move)`; write the commit atomically (`dir: resolvedTarget`, `pendingDelete: [oldDir]`, `move: null`); delete the old `dictata.json` and `dictata-audit.ndjson` (files only, and only after re-checking they are not the resolved dir); write the pointer again with `pendingDelete: []`; return `{ moved: true, dir: resolvedTarget }`. On any failure up to and including verification, delete only the target files this call created, restore the pre-move pointer (previous `dir` and `pendingDelete`, `move: null`), and return `{ moved: false, message }` — the source is never touched. All messages are user-facing, em dash + remedy, and never include another user's full folder path. If the D-14 checkpoint selected `staged-verify-delete`, copy to `dictata.json.moving` / `dictata-audit.ndjson.moving` inside the target, run the identical `verifyCopy` against those names, then `renameSync` each into its final name inside that same directory immediately before the commit; the journal shape, the commit ordering and the recovery rules are unchanged.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| transcribed text → exported file | Attacker-influenceable text becomes a spreadsheet cell or file content |
| settings renderer → main process IPC | A renderer requests an export path or a storage move |
| user-chosen directory → filesystem | An arbitrary path becomes the destination of a copy and a delete |
| audit ledger → exported audit file | Long-lived metadata crosses into a hand-off artifact |
| pointer journal → deletion engine | A stale or mis-ordered record decides which files get deleted |
